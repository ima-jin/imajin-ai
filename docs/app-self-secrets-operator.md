# App self-secret operator controls
The `/jin` **App secrets** section includes active registry apps (including apps claimed before a provision ledger existed) and succeeded provisions. Names, generation recipes, status and lifecycle timestamps are metadata only. The timeline shows minted, granted, fetched, rotated and revoked facts; signed operator changes show who signed and the proposal used (`via`). There is no reveal or copy-value control.
## Approving changes
Only an active, claimed app can receive changes. **Sync manifest secrets**, **Rotate** and **Revoke** stage pending `apps:secrets-sync`, `apps:secrets-rotate` and `apps:secrets-revoke` proposals. Review the card in **Operator approvals**, then sign with your human operator key. A cookie session without a verified countersignature cannot execute the change; agents and act-as sessions cannot decide it. Creating a proposal does not mutate the app or mint material.
Sync reads `imajin.app.json` from the registered app slug's repo and snapshots only validated `secrets` entries (`name`, `random-32B` or `random-64B`). The card hash covers those recipes. Execution re-reads the manifest and refuses an unreadable or changed list; propose again after a manifest change. Sync writes only `registry.apps.secrets`, never scopes, dependency audiences or event permissions, then issues missing secrets using the normal vault custody helpers. Existing generation kinds cannot change through sync. Revoked secrets stay revoked; sync is not a restoration operation.
Rotate replaces one declared active secret under the same app-DID grant policy. Revoke blocks future fetches and does not erase values already held by a running process. Request bodies, responses, approval records and the UI carry no secret values.
## Next boot and sessions
Apps fetch self-secrets at boot. Rotation therefore takes effect on the next app boot/restart, not immediately in a running process. Rotating `SESSION_SECRET` invalidates previously signed sessions after restart: users must sign in again. Revoking a boot-required secret can prevent the next boot from succeeding. Coordinate the restart and user impact before signing.
## HTTP surface
`GET /jin/api/app-secrets` is operator-only metadata. `POST /jin/api/app-secrets` accepts only `{appDid, action}` for sync or `{appDid, action, name}` for rotate/revoke. Callers cannot submit recipes, plaintext, scopes or event permissions. The response is a pending proposal id; execution happens only through the existing `/jin/api/operator-approvals/:proposalId/decision` countersign rail.
