# App self-secret operator controls
The `/jin` **App secrets** section includes active registry apps (including apps claimed before a provision ledger existed) and succeeded provisions. Names, kinds, status and lifecycle timestamps are metadata only. The timeline shows minted, granted, fetched, rotated and revoked facts; signed operator changes show who signed and the proposal used (`via`). There is no reveal or copy-value control.
## Approving changes
Only an active, claimed app can receive changes. **Sync manifest secrets**, **Set**, **Rotate** and **Revoke** create pending proposals. Review the card in **Operator approvals**, then sign with your human operator key. A cookie session without a verified countersignature cannot execute the change; agents and act-as sessions cannot decide it. Creating a proposal does not mutate an active app grant or mint usable material.
Sync reads `imajin.app.json` from the registered app slug's repo and snapshots only validated `secrets` entries (`name` and kind: `random-32B`, `random-64B`, or `operator-supplied`). The card hash covers those recipes, never secret input. Execution re-reads the manifest and refuses an unreadable or changed list; propose again after a manifest change. Sync writes only `registry.apps.secrets`, never scopes, dependency audiences or event permissions, then issues missing generated secrets using the normal vault custody helpers. Operator-supplied declarations await input rather than being generated. Existing kinds cannot change through sync. Revoked secrets stay revoked; sync is not a restoration operation.
Rotate replaces one declared active secret under the same app-DID grant policy. Revoke blocks future fetches and does not erase values already held by a running process.
## Supplying an operator value
For a missing/revoked `operator-supplied` declaration, select **Set**. For an active one, select **Rotate** and supply the replacement. The masked input accepts a nonempty string up to 65,536 UTF-8 bytes. It is cleared immediately on submission and is never returned by the API, redisplayed, copied to a URL, or included in an approval card, attestation, audit payload or provider-error message. Do not place values in manifests, terminal commands, issue comments or logs.
The request necessarily carries the entered value to the kernel over the authenticated transport. Unlike generated kinds, it creates sealed staging material before approval; it does **not** grant that value to the node or app. Pending proposals carry only an opaque staging reference and names-only metadata. The sealed record is bound to the proposal, operator, app DID, name, action and a 24-hour expiry. A pending set is not boot-ready; a pending rotate leaves the current active value in use.
Execution consumes staging once, only after verified human countersign and binding/expiry checks. Rejection or expiry never activates the value. Rejected/expired sealed records are inert; immediate physical deletion is not promised. Consumption tombstones staging before import, so a failed execution may require a fresh value submission and approval rather than retrying the consumed input. Error surfaces are generic and must not echo an underlying vault/provider exception. There is no secret preview or readback step.
## Next boot and sessions
Apps fetch self-secrets at boot. Approval alone does not restart an app or rewrite its environment. Rotation therefore takes effect on the next app boot/restart, not immediately in a running process. Rotating `SESSION_SECRET` invalidates previously signed sessions after restart: users must sign in again. Revoking a boot-required secret can prevent the next boot from succeeding. Coordinate the restart and user impact before signing. An imported provider credential must already be usable by its external service; vault rotation does not change a database password or a provider account for you.
## HTTP surface
`GET /jin/api/app-secrets` is operator-only metadata. `POST /jin/api/app-secrets` accepts:
- `{appDid, action: 'sync'}` for manifest sync.
- `{appDid, action: 'rotate', name}` for a generated-kind rotation, or `{appDid, action: 'revoke', name}` for revocation.
- `{appDid, action: 'set', name, value}` for a missing/revoked operator-supplied secret.
- `{appDid, action: 'rotate', name, value}` for an active operator-supplied secret.
Callers cannot submit recipes, scopes or event permissions. Only set/operator-supplied rotate accept plaintext as sensitive input; no response echoes it. The response is `{status: 'pending', proposalId}`; execution happens only through the existing `/jin/api/operator-approvals/:proposalId/decision` countersign rail. Set uses `apps:secrets-set`; rotate, revoke and sync use `apps:secrets-rotate`, `apps:secrets-revoke` and `apps:secrets-sync`.
## Release and app adoption
The [author guide](app-self-secrets-author.md#adoption-order-follow-up-work-not-an-automatic-cutover) lists the database-first adoption order and additional app/environment keys. It does not report those apps as migrated. First release the SDK/kernel through the normal reviewed Release workflow; feature work never bumps package versions. Per-app entrypoint/config changes, existing-value import, environment cleanup and restart are separate reviewed work. This feature makes no server, env, deploy or standalone-repository changes; #2260 remains separate.
